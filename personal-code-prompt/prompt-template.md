# Prompt 模板

> 按需保留或省略各节。使用前先完成分工，分工不进入正文。

## 分工（开发前完成，不写入正文）

先写清三件事，再动手写正文：

### 模型负责

- [需要语义理解的任务]
- [需要结合上下文判断的任务]

### 模型不负责

- [其他节点处理的任务]
- [当前阶段不应提前判断的内容]

### 代码 / Schema 负责

- [字段类型 / required / 枚举]
- [长度 / 数量限制]
- [去重 / 排序 / 截断 / 编号 / 默认值]

> 判断标准：不需要理解自然语言就能完成的，优先不要让模型做。

## 正文

### 【任务】（必需）

你负责 [一句话说明当前节点解决的问题]。

目标是 [1～3 句说明需要的语义结果]。

只负责：[核心职责]
不负责：[容易越权到的下游任务]

> 只说明当前这一步要解决什么，不描述整个系统怎么运行。

### 【核心原则】（必需）

- 默认：[模糊情况下的判断方向]
- 属于目标结果：[条件]
- 不属于目标结果：[说明语义原因，而不是罗列禁止项]

> 优先写能覆盖多类情况的正面原则，不堆例外。业务允许结果为空时，用"清单外的都不算"给未覆盖情况一个出口；业务不接受空结果时，要求选出相对最优项。

### 【上下文与证据】（按需）

> 只有需要外部资料、长文本、检索结果时才保留。

- [字段 A]：表示……
- [字段 B]：只是背景，不代表……

不得用背景替代核心证据；不得补全材料中没有的信息。

### 【特殊边界】（按需）

> 只有统一原则覆盖不到、且反复误判的场景才写。数量要控制。

当 [条件] 时：[如何理解]

如果特殊规则越来越多，先回去检查是否缺一条更高层原则，而不是继续叠补丁。

### 【判断步骤】（按需）

> 只有确实需要多步判断时保留，只规定内部顺序，不要求输出思维过程。

1. 当前输入描述的对象是什么？
2. 是否满足目标语义？
3. 是否命中排除条件？
4. 是否与已有事实属于同一语义单位？
5. 只保留本节点需要的输出。

### 【输出语义】（必需）

只描述模型需要表达什么，不写完整 Schema。

- [需要模型生成的语义字段]

不要要求生成下游能推导的字段；回填输入 ID 用于核对对应关系的除外。

### 【Few-shot】（按需）

> 默认不放。只有规则无法稳定表达边界或模型反复出错时增加。

用容易混淆的对照案例；少量高价值示例优于大量正例；不得与正文规则冲突。正文或输出结构改动后，示例要同步按新契约检查一遍。

### 【当前输入】（必需）

{{当前实际输入}}

## 最小格式骨架（可选）

当 schema 不实际发给模型时，按真实契约在正文内写最小格式例子：

```json
{"title": "string", "evidence_ids": ["string"]}
```

- 这是按真实契约填的最小格式例子，与语义 few-shot 不同。
- 不能所有 prompt 硬套同一个 JSON。
- schema 发给模型后，正文仍要说明每个字段的语义。
- 最终由代码校验返回结构；结构正确不等于语义正确。
