# 个人代码与 Prompt 约定

本 skill 自包含，单独加载即可使用，不依赖其他 skill。它的作用是在个人项目里让代码结构和 Prompt 写法保持一致的判断方式：能确定的事情用代码保证，需要语义理解的事情才交给模型。

规则之间有轻重。以下几条是硬边界，与其他条目冲突时以它们为准：不越出授权范围、不编造依据、不隐藏核心失败、不删除仍有效的业务约束。函数行数、文件拆分、模板章节属于写法指导，不为符合形式而牺牲正确性。

在已有项目里修改时，先沿用项目现有的结构和约定；与本 skill 不一致的地方在方案里指出，不顺手重构。

代码样例见 `code-template.md`，Prompt 模板与上下游分工见 `prompt-template.md`，按需读取。

## 入口：先分清模型与代码

动手前先把一件事想清楚：这一段逻辑该由模型还是代码承担。

- 需要语言理解、语义判断的，交给模型。
- 能由代码、Schema、规则确定完成的，交给代码。
- 不确定时优先问："这一步真的必须让模型判断吗？"

开工前还要确认授权范围：本次要做什么、允许改哪些文件、是否授权运行测试/回放/外部请求。阅读代码和文件不需要额外授权；未经授权的动作先不做，拿不准就向用户确认，不要自行扩大范围。

## 新建项目起步

按顺序确认后再动手，避免先搭框架再回头改方向：

1. 目标与非目标：这个项目要解决什么，同时明确不做什么。
2. 输入与输出：进来什么、出去什么，边界在哪。
3. 实际业务步骤：按业务真实发生的顺序列出阶段，不按技术分层硬套。
4. 模型与代码分工：哪些阶段真需要模型语义能力，哪些用代码保证。
5. 失败处理：核心步骤失败怎么暴露，辅助步骤失败怎么隔离。
6. 核对授权范围：哪些改动、哪些验证已经获得授权。

只建当前真正需要的文件，不预建通用框架、目录或恢复体系。业务分层按项目实际来。例如晨报这类流程可以是"召回→筛选→选择→写作→发布检查→渲染"，但这是业务分层的示例，不是所有项目都要照抄的固定菜单。

## 代码编写约定

- 主入口从上到下按业务顺序做薄编排：一行对应一个业务阶段，读的人不看细节也能知道流程。细节下沉到对应阶段模块。
- 命名用业务语言，不用内部版本代号；注释写 why（为什么这么做），不写 what（代码已经说明了做什么）。
- 业务常量与 Prompt 版本集中放在 settings 类文件，并解释这个值为什么是这个值，而不是散落在各处。
- 单个函数约 20–80 行只作为阅读提示：不为凑行数拆，也不为追求短而硬拆；文件按业务职责拆，不按行数机械拆。
- 需要一起理解的代码保持在一起，不为追求短函数而拆散。
- 不强制每个模块都写 docstring，只在真正需要说明时写。
- 遵循 YAGNI：不留死代码、不做没有需求的防御。兜底和输入校验必须对应明确业务需要、失败情形和处理结果，例如辅助栏目失败不影响主报、标题缺失按确认规则跳过。不添加泛化防御、层层检查或"以防万一"的兼容层，不自行扩展框架加固、安全测试或通用基础设施；真实业务约束和既有必须的边界不能删除。其他工程工作仅在用户另行明确要求时才做。
- 辅助分支失败要隔离，并显式说明失败影响范围；核心步骤失败不要隐藏。隔离只在辅助分支的边界处做一次，不在核心步骤里层层捕获。
- 外部调用（模型 API、网络请求）的超时和重试次数放在 settings 并写明取值理由；重试用尽后按该步骤属于核心还是辅助来处理，不无限重试。
- 每次模型调用留痕：渲染后实际发送的 Prompt、模型与参数、原始返回、校验结论，能按单次运行回看，写 jsonl 文件即可，不记录密钥。这是 bad case 分层定位的前提，不算预建基础设施。
- 只有确实需要的关键产物才用原子写/完成标记/哈希，不提前搭建恢复体系。

## Prompt 编写约定

- Prompt 只承担核心语义任务，一个 Prompt 只做一个核心判断。基于同一份材料、关系紧密的附带标注可以合并在同一次调用里；只有证据表明两者互相干扰时才拆开，拆分会增加调用次数，也可能带来两次结论对不上的新问题。
- 用正面准入，而不是堆排除项。业务允许结果为空时，提供"清单外/无结果"出口；业务不接受空结果时，要求选出相对最优项，不加空出口，也不在正文里写"可以不给"之类与之矛盾的话。业务不接受空结果、但输入里没有任何候选时，由代码在调用模型前拦下并按失败策略处理，不交给模型硬选。
- 最小充分输入、最小必要输出；下游能推导的信息不重复生成。回填输入中的 ID 用于核对对应关系，不算冗余。
- 修改 Prompt 正文或输出结构时，同时检查随正文发送的示例、代码里的返回校验和纠错文字，与正文保持一致。纠错文字只说明本次具体违反了哪条要求，不夹带其他业务规则，也不把软性建议写成硬性失败。格式纠错重试有次数上限。
- Few-shot 不是必须项，能用正文讲清就不加；确需添加时，只放容易混淆的边界对照案例。
- 同事件的语义去重、重要性排序可能仍需要模型；按字段的确定性去重/排序/截断/编号等交给代码。
- 格式契约要覆盖三件事：定义、实际发送、返回校验，尽量只有一个结构定义源。不强制 Pydantic/SDK/具体模型。
- 结构正确不等于语义正确；若 schema 没有实际发给模型，prompt 里要留最小格式例子（这和语义 few-shot 不是一回事）；即使发送了 schema，正文仍要说明每个字段的语义，并在代码里做最终校验。

## 修改流程

1. 出方案：说明改什么、为什么、影响哪些业务行为。
2. 用户确认：得到明确同意再动手。
3. 实施。
4. 按确认的规则逐条核对。
5. 汇总结果：改了什么、做了哪些核对、哪些核对没做以及原因。

纯整理类改动（改名、搬文件、格式化）不启动业务验收。业务行为改动的核对范围要最小且明确；未执行的核对如实报告，不要把必需的业务核对写成可以省略，也不要在未授权时自行运行核对。

不再适用、重复或没有实际收益的规则，经用户确认后删除，不继续叠加；不能据此擅自删除仍有效的业务规则。

## bad case 定位

出现 bad case 时，先调出该次运行的模型调用留痕，定位问题来自哪一层：Prompt / 上游输入 / 代码 / 下游 / 节点设计。只有确认属于 Prompt 语义问题，才去改 Prompt。

- 不堆排除例外，先找一条能覆盖多个 bad case 的高层原则。
- 一次优先只改一个 Prompt，保持其他条件不变；如果确实需要 schema/调用配套联动，要一并说明。
- 新版本放新目录，旧版不改，通过 settings 常量引用。新版本经回放确认并稳定使用后，不再引用的旧版本目录经用户确认再删除，不长期保留。
- 文件清单按实际 loader 的需要来，不凑固定数量的文件。

## 效果验证

经授权后，用同一批真实输入、固定模型与参数，让旧版与新版跑小范围真实生产链路回放，对比最终业务结果。回放样本既包含原 bad case，也包含原本结果正确的输入，至少看三件事：bad case 是否修复、原本正确的结果是否变差、最终业务产物是否符合预期。

不能因为格式通过就宣称效果改善。模型输出有波动，少量回放只作定性判断，不把一次通过当作效果已被充分证明。

确定性代码改动用已有测试或针对性样例核对，同样在授权范围内运行。

无需评估平台、自动模型评分、pytest 体系或固定样本数。

## 检查清单

完成后逐条核对：

1. 能否一句话说清核心任务？
2. 是否同时承担了互相干扰、本应拆开的多个认知职责？
3. 哪些内容其实可以由代码完成？
4. 是否传了模型当前不需要的数据？
5. 是否让模型生成了下游能推导的字段？
6. 示例、返回校验、纠错文字是否与正文一致？
7. 代码是否薄编排、命名用业务语言、常量集中在 settings 并解释原因？
8. 失败处理是否区分核心暴露与辅助隔离？
9. 模型调用是否留痕，外部调用和格式纠错是否有次数上限？
10. 本次改动范围与验证授权是否明确、未执行的核对是否如实报告？
