# LLM/Agent Prompt 工程

## 核心设计原则

1. **Prompt 只处理语义任务** — 需要语言理解、语义判断、信息提取或生成的任务才放进 prompt。
2. **确定性工作交给代码** — 能由代码、Schema、规则或后处理确定完成的事情，不写进 prompt。
3. **单一职责** — 一个 prompt 只承担一个核心认知任务。
4. **最小充分信息** — 只给模型当前任务真正需要的信息。
5. **最小必要输出** — 输出只保留下游无法可靠推导的最小必要信息。
6. **Few-shot 不是必选项** — 只在规则无法稳定表达边界、或模型反复误判时增加。
7. **生产链路验证** — prompt 是否有效以真实生产链路回放结果为准，不以大量 pytest 为准。

## 工作流程

### 第一步：职责划分

在写 prompt 之前，先明确三个边界：

**模型负责（需要语义理解的）：**
- 需要理解自然语言才能完成的任务
- 需要结合上下文判断的任务
- 需要提取 / 归纳 / 分类 / 生成的语义结果

**模型不负责（由其他节点处理的）：**
- 由其他节点处理的任务
- 当前阶段不应该提前判断的内容

**交给代码 / Schema / 后处理的：**
- JSON Schema（字段类型、required/optional、枚举合法性）
- 数量限制、字符长度限制
- ID 合法性、去重 / 排序 / 截断、默认值
- ID 生成、确定性字段映射
- 可以通过已有字段直接推导的结果

> 判断标准：如果不需要理解自然语言就能完成，优先不要让模型做。

### 第二步：按模板结构编写 Prompt

使用 `prompt-template.md` 中的结构模板编写 prompt。各 section 的使用规则：

| Section | 何时保留 | 何时省略 |
|---------|---------|---------|
| 任务 | **必须** | — |
| 上下文数据 | 需要外部资料、长文本、检索结果时 | 模型只需要当前输入即可判断 |
| 核心语义原则 | **必须** — 这是 prompt 最重要的部分 | — |
| 证据与上下文使用规则 | 存在证据绑定、RAG、长文本或多来源信息时 | 单一输入、无证据引用需求 |
| 特殊业务边界 | 统一原则无法覆盖、生产中反复误判的场景 | 能被上层统一原则覆盖 |
| 判断步骤 | 任务需要多步判断 | 单步判断即可完成 |
| 输出内容 | **必须** — 但只描述模型需要表达什么，不写完整 Schema | — |
| Few-shot | 规则无法稳定表达边界、模型反复在某类场景出错 | 正文已经能明确表达 |
| 当前输入 | **必须** | — |

### 第三步：质量检查

完成后逐条检查（检查清单）：

1. 能否用一句话说清核心任务？
2. 是否同时承担多个可以拆开的认知任务？
3. 哪些内容其实可以由代码完成？
4. 是否传入了模型当前不需要的数据？
5. 是否要求模型生成了下游能够可靠推导的字段？
6. 是否存在重复表达同一规则？
7. 是否存在"要求做 A，同时又要求不要做 A"的冲突？
8. 是否存在正文和 Few-shot 冲突？
9. 是否明确了模糊情况下的默认行为？
10. 是否明确区分核心证据和补充上下文？
11. 特殊规则是否已经变成 bad case 补丁堆积？
12. 是否有字段只是为了"输出看起来完整"而存在？
13. 是否包含模型根本不需要知道的 pipeline 实现细节？
14. Few-shot 是否真的有必要？
15. **删除 20% 的 prompt 后，核心任务是否仍然能完成？如果可以删除，就删。**

## Prompt 修改原则

出现 bad case 时，**不要立即往 prompt 中增加规则**。先判断问题来自哪一层：

| 层级 | 典型问题 |
|------|---------|
| **Prompt 层** | 语义定义不清、默认原则不明确、边界缺失、Few-shot 误导 |
| **输入 / 上游层** | 候选数据错误、RAG 结果错误、信息缺失、上游分类错误 |
| **代码层** | Schema 太宽、validator 缺失、ID/字段处理错误、去重/排序/截断逻辑错误 |
| **下游层** | merge 错误、classification 错误、temporal 判断错误、展示层错误 |
| **节点设计层** | 当前 prompt 承担职责过多、本应拆开的任务被放到同一节点 |

**只有明确属于 prompt 语义问题时，才修改 prompt。**

修改时优先寻找能够覆盖多个 bad case 的高层规则，不要无限追加例外。

## 验证方式

Prompt 修改后使用 **小范围生产链路回放** 验证，不以新增大量 pytest 作为业务验收方式。

流程：旧版本 + 新版本 → 同一批真实生产输入 → 跑真实小范围生产链路 → 对比最终业务结果。

重点检查：
- 原来的 bad case 是否改善
- 原来正确的 case 是否回退
- 是否产生新的漏提取 / 误提取
- 是否出现过度拆分 / 错误合并
- 是否出现背景信息污染
- 最终业务结果是否符合实际需求

**一次只修改一个 prompt，验证通过后再修改下一个。**

## 最终判断标准

> 模型负责不确定的语义问题，代码负责确定的工程问题。

> Prompt 的目标不是把所有规则都写进去，而是给模型完成当前语义任务所需要的最少且充分的信息。

每次开发 prompt 时，优先问：**"这件事真的必须让模型知道和判断吗？"** 如果不需要，就不要放进 prompt。
